# 长器乐轨 EOS 失败修复（Hybrid 4.0.1）

## 问题与复现

用户实际失败任务的选段为原曲 0–245.38 秒。六轨分离、主唱、贝斯和吉他已完成，
钢琴分支在内部第 16 个五秒窗口（80 秒）达到 2000 token 上限，未输出 EOS，因而没有提交完整曲谱。
主程序此前只显示“混合后端阶段失败，详见阶段日志”，主日志也没有记录具体分支及可持久访问的诊断路径。

保留前序上下文的诊断复现了同一失败。将预算提高到 4000 仍在同处失败，重复 token 中包含
大量鼓点（例如 drum 44）；这不是用更大预算就能解决的正常音符密度问题。
同模型、同输入的 MPS FP32 贪心解码通过该钢琴窗口，并完成整条钢琴轨。
继续验证发现“其他”轨也有独立的贪心循环，CPU 或只改 FP32 仍不足以处理全部段落。

## 修复

- 四组器乐输入（贝斯、吉他、钢琴、其他）使用运行库原生 forbidden-token 机制，在生成前只屏蔽 drum token。
  允许全部有音高的 program 标签，包括没有公开名称的组；不把钢琴输入强行标为钢琴，也不删除生成后的鼓事件来掩盖循环。
- 正常路径仍为贪心解码、beam=1。MPS FP16 的严格 EOS 失败后，使用同一权重、完整输入重试 FP32。
  若仍失败，再使用原生 beam=2 完整重试。CPU/CUDA 只有一次 beam=2 重试。
  重试保留 batch=1、prelude_forcing、sampling=false、2000 token 上限与严格 EOS。
- 每次重试都重新加载同一模型，丢弃失败尝试的全部事件，保留来源、精度、beam 和失败位置记录。
  不切片拼 MIDI、不强行补 EOS、不填休止、不换模型。OOM、缺文件和其他错误不触发此解码重试。
  原有自动模式的明确 GPU 故障 CPU 回退策略继续适用。
- 失败提示指出实际音轨、原曲时间和解码上限。旧组件只返回笼统错误时，新主程序也可从 stderr 尾部恢复 EOS 原因。
- 故障摘要和每份最多 64 KiB 的阶段日志保存在 `transcription/diagnostics/<task>/`，
  主日志记录这个路径；删除临时任务后仍可诊断。不复制音频或登录凭据。
- 主程序接受 4.0.1，同时兼容 4.0.0 / 3.x。4.0.0 显示升级提示；要使用新解码需更新主应用并导入新组件。

## 验证

自动回归覆盖：完整输入重试、失败事件丢弃、有限尝试、非 EOS 错误不重试、原生参数保持、
只屏蔽鼓点 token、原曲偏移、旧组件错误翻译，以及临时任务关闭后日志仍保留。
完整测试集 480 项通过，Ruff 与 Git 空白检查通过。

真实用户音频验证：

- 原钢琴轨的 MPS FP16 在 80 秒失败；同一 small 权重的完整 FP32 重试完成全部 49 个窗口。
- 最终 4.0.1 压缩包经实际安装后，再以自动设备选择运行完整钢琴轨；鼓点屏蔽下的 FP16 / FP32
  贪心分别在 80 / 200 秒失败，最后 FP32、beam=2 完成全部 49 个窗口，输出保留原选段的 245.375 秒时长。
- 原“其他”轨使用 FP32、原生 beam=2、鼓点屏蔽，完成整条 245 秒输入的 50 个窗口，
  约 175 秒，1643 个原始候选，未产生鼓点事件，单窗口最多 634 token。
- 候选数量和成功结束不等于准确率，仍需试听与人工修正。
- macOS 应用启动截图、组件安装校验、应用签名校验及 DMG 校验均通过；应用与组件均为 arm64。

完整诊断、对照和构建产物保存在 `artifacts/multistem-eos-2026-10-29/`（不入版本库）。
Mac 新应用输出在 `dist/multistem-4.0.1/`，避免覆盖仍在运行的旧应用；
配套组件为 `dist/AutoSkyPlay-Hybrid-4.0.1-macos-arm64.zip`。

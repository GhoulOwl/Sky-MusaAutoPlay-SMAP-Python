# MOSS-Music 和弦与段落实验

此分支提供可选实验模式，尚未完成 Windows 真机或人工听感验收。“主旋律＋和弦”模式使用本地音符／声学证据，并让 MOSS 在有证据的三和弦候选之间消歧；现有的三键、音区、音尾、真实静音与人工休止约束仍然生效。“主旋律＋MOSS 直接和弦（实验）”按照模型输出的和弦变化生成伴奏，不再经过上述和声证据、音区、音尾或三键筛选。“主旋律＋MOSS 优化和弦（实验）”保留直接模式作为对照，另行优化与旋律同键的重叠及半音近似。曲式标签仅用于定位，不修改源段落分类。

## 准备模型

“设置 → 扒谱模型管理”中的“MOSS 原始权重”从魔搭 `openmoss/MOSS-Music-8B-Instruct` 固定修订下载约 18.1 GB；支持续传并逐文件 SHA-256 校验。魔搭目前未发现可用的该模型 Windows Q4 GGUF 镜像，所以原始权重不能直接用于本实验。需在本机另行转换，建议预留约 60 GB 可用磁盘空间；具体峰值还取决于转换工具和原始权重所在磁盘。

以下方法使用 HOT-Step-CPP 的转换器、Q4 量化程序和 `ace-caption`，以代码修订 `d3c8cfc23419a6c0ec920d108648d4fd861b3522` 为参考。需要 Git、CMake、C++ 编译器、Python、`gguf`；CUDA 构建还需 CUDA 工具链。步骤仅作为实验开发流程，尚未在 Windows 真机验证：

1. 获取并检出上述修订，执行 `git submodule update --init --recursive` 初始化子模块。按 [HOT-Step-CPP 构建说明](https://github.com/scragnog/HOT-Step-CPP)构建 `ace-caption` 和 `quantize`，保留它们所需的动态库。Windows NVIDIA 可参考上游 `engine/buildcuda.cmd`。
2. 在 AutoSkyPlay 源码目录运行下列命令（替换尖括号内的路径；数据目录可从“软件信息 → 打开文件位置”查看）：

   ```powershell
   uv run --with gguf python scripts/prepare_moss_q4.py --data-dir "<AutoSkyPlay数据目录>" --converter "<HOT-Step目录>\engine\tools\convert-moss.py" --quantizer "<quantize.exe路径>" --output "<新的模型输出目录>"
   ```

   命令重新校验魔搭原始权重，先转换 F16，再用上游量化器生成 `moss-lm-q4_k_m.gguf`；音频编码器为 `moss-aud-f16.gguf`。转换时将中间张量暂存到磁盘，以减少内存压力。输出目录必须不存在，成功后才发布。转换完成后原始权重仍会保留，可在模型管理中删除。
3. 选歌并准备波形后，可先选择不超过 7 分钟的范围，再点击“MOSS 和弦／段落分析…”，选择 `ace-caption` 和转换后的模型目录。“曲式定位”下拉列表可在波形中选中模型推测的段落，然后开始扒谱。先选段分析的结果不会自动带入新草稿；若要辅助和弦，请在扒谱完成后对草稿再运行一次 MOSS，再选择“主旋律＋和弦”、“主旋律＋MOSS 直接和弦（实验）”或“主旋律＋MOSS 优化和弦（实验）”试听。分析草稿时使用草稿对应的源音频片段，时间从片段起点计算；只有旧版三和弦数据的草稿需重新分析才能取得扩展和弦，已有完整 MOSS 数据的草稿无需重跑模型。

模型输出的是和弦名称和变化时间，并未给出实际音符、八度、节奏型或时值。直接模式在每个变化点同时演奏所识别的和弦音，持续到下一个变化点；最后一个和弦暂延续至选段末尾，这是程序推定而非模型输出。支持常见七和弦、减和弦、斜杠低音及若干扩展和弦；不认识的符号会保留并标记，不能自动转成音符。由于光遇只有 15 个白键，半音会就近近似、超出音域的音会折回，映射后同一时刻重复的键只保留一次；这并不等于忠实还原原和弦。直接模式可能同时超过三键、与旋律同键或覆盖人工休止，应试听并检查。原常规模式仍对最后一项参考最多 4 秒，且只使用大／小三和弦。

MOSS 直接和优化模式暂不支持局部精修，避免精修流程在拼接时遗漏这些伴奏；可切换到其他编配模式再精修。

超出音频末尾的曲式会裁剪；输出没有可解析内容时会报错并保留原草稿。若已人工编辑，会创建新草稿。识别结果和曲式标签均可能出错，需要试听、核对，不能将自动测试当作音乐质量验证。

## 本机试验记录

使用魔搭官方 Instruct 权重转换的 Q4，在 Apple M4 / 16 GiB 内存机器上通过 HOT-Step-CPP `ace-caption` 运行。三首歌曲各取开头和 60 秒起的 24 秒片段，与已有 MuScriptor 原混音音符事件做离线对照；这不是 Hybrid 六轨真机验证。开头片段使用分别询问和弦与曲式的诊断提示词；额外用界面采用的提示词重新验证了 love 开头的完整工作流。未提供逐音参考谱或人工盲听评分。

| 片段 | 原版伴奏数 | MOSS 版伴奏数 | 主旋律变化 | MOSS 候选获本地证据支持的和弦跨度 |
| --- | ---: | ---: | --- | ---: |
| love 0–24 秒 | 12 | 12 | 无 | 0 |
| island 0–24 秒 | 11 | 11 | 无 | 1 |
| zugou 0–24 秒 | 2 | 2 | 无 | 0 |
| love 60–84 秒 | 24 | 24 | 无 | 0 |
| island 60–84 秒 | 7 | 7 | 无 | 0 |

六个片段的最终音符均完全相同；候选证据、音区、音尾或并发限制使本实验没有增加伴奏，因此**尚无证据表明听感更丰满**。模型有时输出超过实际片段长度的段落终点；程序将其裁剪。两个中段片段没有解析出可用曲式，曲式标签没有人工核对，不能据此衡量定位准确率。输入经本机 FFmpeg 处理，模型在本机运行，未上传音频。Mac 单次推理进程约 6.8 GiB RSS，不代表 Windows 的内存或显存要求。

本轮机器生成的音频、模型输出和逐片段对照数据保存在 `artifacts/moss-experiment/`（不纳入版本控制）；听感需要人工试听确认。Windows 的组件构建、设备选择、取消和性能，以及最新 Hybrid 六轨上的效果都仍待验证。

## 优化和弦与直接和弦对照

优化模式继续使用同一份 MOSS 和弦变化和原旋律，最多选择四个伴奏声部。优先使用光遇白键能精确演奏的和弦音，尝试不同八度以避开旋律占用的同一键；必要时在旋律或人工休止处切分伴奏。对于衰减音色，还参考各键采样下降至峰值以下 18 dB 的强音尾，避免同键伴奏攻击与旋律强音尾重叠。该检查针对本项目音色采样及谱面时钟，不保证游戏里的音色、延迟或混响完全相同。

当一个和弦至少有一个可精确演奏的音级，优化版省略无法精确映射的半音，并可用已有和弦音的另一个八度加厚；这可能减少和弦中的不同音级，改变原和弦色彩。当整个和弦都落在黑键上时，为避免静音，仍使用最近白键近似。无法识别的和弦符号不猜测；所有候选均被占用或处于人工休止时，该和弦可能没有伴奏。界面显示省略数量和八度加厚数量，悬停统计可查看受影响和弦。声部与片段数不同：一个声部为避让旋律可能被切分成多个音符。

使用上面同样的三首歌、各两个 24 秒片段和相同模型输出比较；两版均为钢琴、移调 0、原始节奏。表中的“同键重叠”统计与旋律持续时间重叠的伴奏音符数；“半音近似”仅统计伴奏音符，不含旋律。

| 片段 | 直接：伴奏 / 同键重叠 / 半音近似 | 优化：伴奏 / 同键重叠 / 半音近似 |
| --- | --- | --- |
| love 0–24 秒 | 13 / 8 / 1 | 15 / 0 / 0 |
| love 60–84 秒 | 64 / 11 / 5 | 65 / 0 / 0 |
| island 0–24 秒 | 35 / 4 / 21 | 25 / 0 / 0 |
| island 60–84 秒 | 30 / 10 / 19 | 22 / 0 / 0 |
| zugou 0–24 秒 | 34 / 7 / 20 | 24 / 0 / 0 |
| zugou 60–84 秒 | 29 / 15 / 22 | 17 / 0 / 4 |

六段合计，伴奏与旋律同键重叠从 55 个降到 0 个，按强音尾估算的同键重叠从 57 个降到 0 个，伴奏半音近似从 88 个降到 4 个；六段的主旋律音符数据不变。伴奏音符由 205 个变为 168 个，其中一些是切分后的片段；记谱总时值从约 514 秒降到 373 秒，不能直接当作实际响度或丰满度。优化版使用了 49 个八度加厚的音符片段，六段最多同时五个不同键，采样峰值最高约 0.690，未发现采样削波。上述统计不证明和弦准确、听感更好或游戏中一定可演奏；尚无人工盲听和逐音参考谱。
